HMS timelines: why they stretch into years — and how to shorten them

The mechanism behind HMS overruns, what to do before you buy, and the gated implementation model Ospia uses to keep time and scope honest.

Ask an IT head why a hospital software project ran long and the answer is rarely “the code wasn’t ready.” It is almost always scope that surfaced late: old customizations nobody catalogued, one-off integrations that break under load, numbering and tariff rules that live in someone’s head, or historical data everybody assumes will be migrated in full.

When these things appear after the contract is signed, two things happen. First, time slips while teams debate what is in scope. Second, costs stack up as vendors and hospital teams scramble to retrofit the plan. The result: a project that was supposed to take months drifts towards a year or more.

The mechanism: late discovery guarantees overrun

  • Hidden customizations: years of tweaks embedded in the legacy HMS become visible only when users try to replicate them. Each one adds testing and training overhead.
  • Brittle integrations: lab, pharmacy, finance, GST e-invoice, TPAs — if the interfaces are undocumented, migration exposes the gaps and edge-cases.
  • Rule-work in people, not paper: numbering schemes, approval matrices, package and pathway logic exist, but are not signed as configuration before build starts.
  • Data assumptions: free-text clinical notes, deep historical detail, legacy custom code and old audit logs are treated as “of course we’ll migrate this”, when each demands an explicit decision.
Overrun is not caused by migration alone. It is caused by discovering scope while you are already paying to deliver it.

What to do before you buy (even if you never call Ospia)

  • Run a pre-signing assessment. Inventory current data, integrations, customizations and workflows and score them for migration complexity. Exit with a complexity map and a timeline you can defend.
  • Draft configuration against your real rules. Numbering, tariffs, approval matrices, packages and pathways should be written down, reviewed and signed before any build.
  • Make explicit migration calls. Flag free-text notes, deep history, legacy customizations and historical audit logs for explicit decisions: migrate, summarise or archive.
  • Insist on gates. Name the implementation phases and require exit criteria for each. No parallel run without verified imports. No go-live while any gate is red.

If your current vendor will not do this pre-signing, do it yourself. The output — a complexity map, signed configuration, and a list of non-negotiable exit criteria — is the cheapest project insurance you can buy.

Questions we get asked

How long does an Ospia implementation take?

Timelines depend on what the assessment uncovers — data shape, integrations, legacy customizations and decisions on historical content. We front-load discovery before you sign and run a gated plan with exit criteria; we do not publish a generic duration.

What does the pre-signing assessment include?

An inventory of current data, integrations, customizations and workflows scored for migration complexity, resulting in a complexity map and a proposed timeline. This is provided before you commit so you are not discovering scope mid-project.

Which items should not be auto-migrated?

We flag free-text clinical notes, deep historical detail, legacy custom code and historical audit logs for explicit decisions. Each carries cost and risk and should be treated case by case: migrate, summarise, or archive.

How do you prevent a rushed go-live?

By gating. Assessment, planning, migration, parallel run, verification, training, go-live and hypercare each have exit criteria, and no hospital goes live while any gate is red. Launch readiness must be proven rather than declared.

Who runs the day-to-day during implementation?

Ospia’s Implementation Agent executes configuration and migration checklists, validates data and tracks readiness through go-live, coordinating with your clinical, finance and IT leads against the signed plan.
